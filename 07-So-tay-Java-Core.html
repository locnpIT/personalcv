Primitive, wrapper và Integer cache

8 kiểu nguyên thủy (byte short int long float double char boolean) lưu giá trị trực tiếp. Mỗi kiểu có một lớp bọc (Integer, Long…) là object trên heap. Java tự đổi qua lại (autoboxing), và đó là nguồn của ba bẫy kinh điển.

Phỏng vấn sẽ hỏi
  • Integer a = 127, b = 127; a == b? Còn 128?
  • Autoboxing có tốn gì không?
  • Khi nào unboxing ném NullPointerException?
ĐO THẬT

Output chạy thật

Integer i3 = 128, i4 = 128;  i3 == i4   → false
i3.equals(i4)                           → true
Long l = 127L;  l.equals(127)           → false   // Long so với Integer
Integer nul = null; int x = nul;        → NullPointerException
int s = map.get("sushi");  // key không có → NullPointerException
Integer r = cond ? nullInteger : 0;     → NullPointerException

Dòng cuối là bẫy khó thấy nhất: một vế là int nên cả biểu thức ba ngôi có kiểu int, Java unbox vế Integer null.

String: bất biến, pool và nối chuỗi

String trong Java là bất biến: mọi thao tác "sửa" đều tạo String mới. Các literal giống nhau dùng chung một object trong String pool.

So sánh bằng ==

ĐO THẬT

Output chạy thật

String s1 = "hugeclub", s3 = new String("hugeclub");
String part = "huge";
s1 == "hugeclub"            → true    // cùng literal trong pool
s1 == s3                    → false   // new luôn tạo object mới
s1 == part + "club"         → false   // nối lúc chạy → object mới
s1 == "huge" + "club"       → true    // compiler gộp sẵn thành literal
s1 == (part + "club").intern() → true
s.toUpperCase();  // không gán lại  → s vẫn là "hugeclub"

Vì sao String bất biến

  • An toàn khi dùng chung: pool chỉ có thể tồn tại vì không ai sửa được object dùng chung.
  • An toàn với luồng mà không cần khoá.
  • Bảo mật: tên file, URL, tên class đã kiểm tra rồi thì không bị đổi sau lưng.
  • Cache hashCode: tính một lần, nên String là key HashMap lý tưởng.
  • Compact strings (Java 9+): chuỗi chỉ có ký tự Latin-1 lưu 1 byte/ký tự thay vì 2. ĐO THẬT 1 triệu chuỗi như "sushi-5-tokyo": 67,5 MB mặc định, 83,5 MB khi tắt -XX:-CompactStrings. Chuỗi có chữ tiếng Việt có dấu luôn dùng 2 byte/ký tự.

Chương 03

equals và hashCode

== so địa chỉ (cùng một object). equals so nội dung theo cách class định nghĩa. Mặc định Object.equals chính là ==.

Hợp đồng bắt buộc

  1. a.equals(b) thì bắt buộc a.hashCode() == b.hashCode().
  2. Ngược lại không bắt buộc: hai object khác nhau được phép cùng hashCode (đụng độ).
  3. equals phải phản xạ, đối xứng, bắc cầu, nhất quán, và x.equals(null) == false.
  4. Field dùng trong equals/hashCode không nên đổi khi object đang nằm trong HashMap/HashSet.
@Override public boolean equals(Object o) {
  if (this == o) return true;
  if (!(o instanceof Reservation r)) return false;
  return Objects.equals(id, r.id);
}
@Override public int hashCode() { return Objects.hash(id); }
ĐO THẬT

Vi phạm hợp đồng thì HashMap "mất" dữ liệu

// Key chỉ override equals, không override hashCode
map.put(new Key("u1"), "An");
map.get(new Key("u1"))          → null

// Key2 override cả hai
map2.get(new Key2("u1"))        → An

// đổi field của key sau khi đã add vào HashSet
set.add(mk); mk.id = "u2";
set.contains(mk)                → false, size = 1

Object nằm trong bucket tính theo hashCode cũ; tìm bằng hashCode mới thì không thấy, và cũng không xoá được: rò bộ nhớ. Dùng field bất biến (id) hoặc record làm key.

JPA entityKhông dùng id tự sinh trong equals/hashCode của entity một cách ngây thơ: trước khi persist id là null, sau khi persist hashCode đổi, entity trong HashSet bị "lạc". Cách phổ biến: so theo id nhưng hashCode trả hằng số theo class, hoặc dùng khoá nghiệp vụ bất biến. Không dùng @Data của Lombok cho entity (nó đưa cả quan hệ lazy vào equals/hashCode/toString).
Chương 04

HashMap bên trong

Một mảng bucket. Mỗi key được băm, lấy vị trí (n − 1) & hash; các key cùng bucket nối thành danh sách, dài quá thì thành cây đỏ-đen. Thêm key và xem bảng lớn lên.

Phỏng vấn sẽ hỏi
  • HashMap hoạt động thế nào? Đụng độ xử lý ra sao?
  • Load factor là gì? Khi nào resize?
  • Java 8 thay đổi gì (treeify)?
  • HashMap có thread-safe không? Dùng gì thay?
ĐO THẬT
20 000 lần get() trên HashMap 20 000 key

mili giây, thang log

hashCode tốt: 0,52 ms. hashCode luôn 42 nhưng key Comparable: cây đỏ-đen sắp theo compareTo, O(log n): 4,8 ms. hashCode luôn 42 và key không Comparable: cây không biết đi nhánh nào, phải tìm cả hai phía: 3,2 giây, chậm hơn 6 000 lần.

Các con số cần nhớ

  • Dung lượng mặc định 16, luôn là luỹ thừa của 2 (để (n−1) & hash thay cho phép chia lấy dư).
  • Load factor 0,75: số phần tử vượt 75% dung lượng thì gấp đôi bảng và chia lại các phần tử (resize). Biết trước số lượng thì khởi tạo sẵn: HashMap.newHashMap(n) (Java 19+).
  • Hash được trộn: h ^ (h >>> 16) để bit cao cũng ảnh hưởng vị trí.
  • Một bucket dài quá 8 phần tử: nếu bảng còn nhỏ hơn 64 thì resize; nếu đã ≥ 64 thì chuyển bucket đó thành cây đỏ-đen (Java 8+). Còn ≤ 6 phần tử thì về lại danh sách.
  • Cho phép một key null (bucket 0) và nhiều value null. ConcurrentHashMap và Hashtable không cho null.
  • Không thread-safe: ghi đồng thời có thể mất dữ liệu (Java 7 còn có thể tạo vòng lặp vô hạn khi resize). Dùng ConcurrentHashMap.

Hình động: vì sao xoá trong for-each lại ném ConcurrentModificationException

ĐO THẬT

Output chạy thật

for (s : [a,b,c,d]) if (s == "b") list.remove(s);
  → ConcurrentModificationException
for (s : [a,b,c,d]) if (s == "c") list.remove(s);
  → không lỗi! list = [a, b, d]   // d bị bỏ qua, không được duyệt
list.removeIf(s -> s.equals("b"))   → [a, c, d]

Arrays.asList("a","b").add("c")    → UnsupportedOperationException
Arrays.asList("a","b").set(0,"z")  → [z, b]      // sửa được, không thêm được
List.of("a").set(0,"z")            → UnsupportedOperationException

Collections.unmodifiableList(src); src.add("b") → view = [a, b]  // chỉ là "khung nhìn"

Xoá an toàn khi đang duyệt

  • list.removeIf(predicate) (gọn nhất).
  • Iterator it = list.iterator(); … it.remove();.
  • Duyệt ngược theo chỉ số.
  • Tạo danh sách mới bằng stream filter.

"Fail-fast" chỉ là cố gắng phát hiện, không phải đảm bảo: như trường hợp xoá phần tử áp chót, vòng lặp kết thúc sớm mà không có lỗi nào, và bạn mất một phần tử chưa duyệt.

Java luôn truyền tham trị. Immutability và final

    
Java luôn truyền tham trị (pass-by-value). Với object, giá trị được sao chép là tham chiếu: method nhận một bản sao của "địa chỉ", nên sửa được nội dung object nhưng không đổi được biến bên ngoài trỏ đi đâu.

  

    

    

    

  

  

    
ĐO THẬT
Output chạy thật


swap(b1, b2);   → b1 = Box(1), b2 = Box(2)   // không đổi gì
change(b3);     → b3 = Box(42)
  // a.v = 42 sửa object chung; a = new Box(7) chỉ đổi bản sao

    
final và immutability

      
  • final biến: không gán lại được; object nó trỏ tới vẫn sửa được (final List vẫn add được).
  • final method: không override được. final class: không kế thừa được (String).
  • Class bất biến: mọi field private final, không setter, sao chép phòng thủ khi nhận/trả collection hoặc object có thể sửa, class final. Java 16+: record làm phần lớn việc này (nhưng List bên trong record vẫn sửa được nếu không bọc).
  • Lợi ích: an toàn với luồng, làm key HashMap an toàn, dễ suy luận.

Exception

    
Throwable chia hai nhánh: Error (lỗi hệ thống, không nên bắt: OutOfMemoryError, StackOverflowError) và Exception. Trong Exception, nhánh RuntimeException là unchecked, còn lại là checked (bắt buộc khai báo hoặc bắt).

  

    

    

    

  

  

    
ĐO THẬT
200 000 lần báo lỗi từ độ sâu 10 tầng gọi hàm
mili giây

      
Phần đắt của exception là chụp stack trace (fillInStackTrace): 1,7 µs mỗi lần. Tắt stack trace còn 0,58 µs; trả mã lỗi bình thường 0,015 µs. Đừng dùng exception cho luồng nghiệp vụ chạy rất thường xuyên (kiểm tra tồn tại bằng exception trong vòng lặp lớn); còn lỗi thật thì cứ ném, stack trace đáng giá hơn vài micro giây.

    
Thực hành tốt

      
  • Bắt cụ thể, không catch (Exception e) {} nuốt lỗi.
  • Ném lại thì bọc kèm nguyên nhân: throw new OrderException("…", e), đừng làm mất stack trace gốc.
  • Log hoặc ném, không làm cả hai ở mọi tầng (log trùng).
  • Exception nghiệp vụ trong Spring thường là unchecked (để @Transactional rollback mặc định và không làm rối chữ ký method), xử lý tập trung ở @RestControllerAdvice.
  • Đóng tài nguyên bằng try-with-resources; lỗi khi đóng không làm mất lỗi chính mà nằm trong getSuppressed().
  • Không return trong finally: nó nuốt mất exception đang bay.

  







  
Chương 09
Generics: type erasure và PECS

    
Generics chỉ tồn tại lúc biên dịch. Sau khi biên dịch, List<String> và List<Integer> đều là List (type erasure).

  

    
Thử với javac: thao tác nào biên dịch được?

    
Mọi ô dưới đây là kết quả biên dịch thật bằng javac 21, kèm thông báo lỗi nguyên văn.

    

      
    

    

    

  

  

    
PECS: Producer Extends, Consumer Super

      
  • <? extends T>: danh sách cho ra T (đọc được T), không nhét gì vào được (trừ null), vì không biết chính xác là List của kiểu con nào.
  • <? super T>: danh sách nhận vào T (add T được), đọc ra chỉ biết là Object.
  • Ví dụ chuẩn: Collections.copy(List<? super T> dest, List<? extends T> src).
  • List<Integer> không phải List<Number> (generics bất biến), dù Integer là Number. ĐO THẬT javac: ArrayList<Integer> cannot be converted to List<Number>.

    
ĐO THẬT
Type erasure và heap pollution


new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()
  → true

List raw = new ArrayList<String>();  raw.add(42);   // chỉ cảnh báo
List<String> strs = raw;  String z = strs.get(0);
  → ClassCastException   // lỗi nổ ở chỗ đọc, xa chỗ gây ra

      
Hệ quả của erasure: không new T(), không instanceof List<String>, không tạo mảng T[], không overload hai method chỉ khác tham số generic. Muốn giữ kiểu lúc chạy thì truyền Class<T> (Jackson dùng TypeReference).

Reflection, annotation và dynamic proxy

    
Đây là ba viên gạch mà Spring, Hibernate, Jackson xây trên đó. Hiểu chúng là hiểu vì sao @Transactional có lúc không chạy.

  

    
ĐO THẬT
Tự viết một "@Transactional" bằng JDK dynamic proxy


OrderService real = id -> "placed " + id;
OrderService px = (OrderService) Proxy.newProxyInstance(loader,
    new Class[]{OrderService.class},
    (proxy, method, args) -> {
      log("BEGIN"); Object r = method.invoke(real, args); log("COMMIT"); return r;
    });
px.place("A1");

// output thật:
   [proxy] BEGIN transaction trước place
   [proxy] COMMIT
   placed A1
   class của proxy: $Proxy0

    
Liên hệ với Spring

      
  • Spring bọc bean bằng proxy (JDK proxy nếu theo interface, CGLIB tạo lớp con nếu không) và chèn logic transaction, cache, bảo mật quanh lời gọi.
  • Gọi this.method() từ bên trong bean là gọi thẳng object thật, không đi qua proxy: annotation bị bỏ qua (chi tiết trong sổ tay Spring Boot).
  • CGLIB không override được method final/private: annotation trên đó cũng vô tác dụng.
  • Annotation chỉ là siêu dữ liệu; phải có code đọc nó qua reflection (getAnnotation) lúc chạy (cần @Retention(RUNTIME)) hoặc annotation processor lúc biên dịch (Lombok, MapStruct).
  • Reflection chậm hơn gọi thẳng và phá đóng gói; framework cache Method, và Java 17+ chặn truy cập sâu vào nội bộ JDK nếu không mở module.

Thời gian: java.time và múi giờ

    
Job gửi mail của bạn lấy dữ liệu "từ đầu tới cuối ngày hôm qua". Hôm qua theo giờ nào? Server ECS chạy UTC, người dùng ở Nhật (UTC+9), đội dev ở Việt Nam (UTC+7).

  

    

    

    

  

  

    
ĐO THẬT
Cùng một thời điểm, ba ngày khác nhau


Instant now = 2026-10-13T16:30:00Z
Asia/Tokyo        = 2026-10-14T01:30+09:00
Asia/Ho_Chi_Minh  = 2026-10-13T23:30+07:00
LocalDate theo UTC = 2026-10-13, theo Tokyo = 2026-10-14

"Hôm qua" theo Tokyo = 2026-10-13
  → từ 2026-10-12T15:00:00Z tới 2026-10-13T15:00:00Z

    
Chọn kiểu nào

      

        
InstantMột thời điểm tuyệt đối (UTC). Lưu DB, log, so sánh.

        
ZonedDateTimeThời điểm + múi giờ khu vực. Hiển thị, tính "đầu ngày theo Tokyo".

        
LocalDate / LocalDateTimeKhông có múi giờ: ngày sinh, giờ mở cửa nhà hàng "11:00". Không dùng cho thời điểm sự kiện.

  • Tiêm Clock vào service để test được logic "hôm qua".
  • Date, Calendar, SimpleDateFormat là API cũ; SimpleDateFormat không thread-safe.
