IoC và Dependency Injection

Thay vì class tự new những thứ nó cần, một container tạo sẵn và đưa vào. Quyền điều khiển việc tạo object bị "đảo ngược" từ code của bạn sang container.

Phỏng vấn sẽ hỏi
  • IoC là gì? DI là gì? Khác nhau thế nào?
  • Constructor, setter, field injection: dùng cái nào, vì sao?
  • Có hai bean cùng kiểu thì Spring chọn cái nào?
  • BeanFactory khác ApplicationContext ra sao?

Không có IoC

class OrderService {
  // tự tạo: dính chặt vào MySQL, SMTP
  private final OrderRepository repo = new MySqlOrderRepository();
  private final MailService mail = new SmtpMailService("smtp.x");
}
// test: không thay được bằng bản giả
// đổi sang SES: phải sửa OrderService

Có IoC + constructor injection

@Service
class OrderService {
  private final OrderRepository repo;
  private final MailService mail;
  // chỉ một constructor: không cần @Autowired
  OrderService(OrderRepository repo, MailService mail) {
    this.repo = repo; this.mail = mail;
  }
}
// test: new OrderService(fakeRepo, fakeMail)

Có nhiều bean cùng kiểu thì sao?

Spring tìm theo kiểu trước. Có hơn một ứng viên thì xét lần lượt: @Qualifier → @Primary → tên tham số trùng tên bean. Không quyết được thì báo NoUniqueBeanDefinitionException. Không có bean nào thì báo NoSuchBeanDefinitionException.

interface PaymentGateway { String method(); Receipt pay(Order o); }
@Component class CardGateway   implements PaymentGateway { public String method() { return "CARD"; } ... }
@Component class PayPayGateway implements PaymentGateway { public String method() { return "PAYPAY"; } ... }

@Service
class CheckoutService {
  private final Map<String, PaymentGateway> gateways;
  // Mẹo hay: tiêm TẤT CẢ bean cùng kiểu vào List, rồi dựng Map → Strategy pattern không cần if/else
  CheckoutService(List<PaymentGateway> all) {
    this.gateways = all.stream().collect(toMap(PaymentGateway::method, g -> g));
  }
  Receipt pay(Order o) { return gateways.get(o.paymentMethod()).pay(o); }
}
// thêm phương thức thanh toán mới = thêm một class @Component, không sửa CheckoutService
BeanFactory và ApplicationContextBeanFactory là giao diện gốc, chỉ biết tạo và trả bean (mặc định tạo lười khi được gọi). ApplicationContext mở rộng nó: tạo sẵn mọi singleton lúc khởi động, có event, i18n, đọc resource, tự đăng ký BeanPostProcessor. Spring Boot luôn dùng ApplicationContext; cụ thể với web là AnnotationConfigServletWebServerApplicationContext.

Vòng đời bean

Bấm "Bước tiếp" để đưa một bean đi qua từng giai đoạn. Mỗi giai đoạn cho biết lúc đó bạn được dùng những gì và hook nào chạy.

Phỏng vấn sẽ hỏi
  • Kể vòng đời của một bean.
  • @PostConstruct chạy khi nào? Vì sao không làm việc đó trong constructor?
  • BeanPostProcessor là gì? AOP proxy được tạo lúc nào?

Bẫy: dùng dependency trong constructor khi tiêm bằng field

@Service
class PriceCache {
  @Autowired PriceRepository repo;    // field injection
  PriceCache() {
    repo.findAll();                  // NullPointerException: field chưa được tiêm
  }
  @PostConstruct
  void warmUp() { repo.findAll(); }   // đúng: lúc này mọi thứ đã sẵn sàng
}

Bẫy: gọi method @Transactional trong @PostConstruct

@Service
class SeedService {
  @PostConstruct
  void init() { seed(); }       // chạy KHÔNG có transaction
  @Transactional
  public void seed() { ... }
}

@PostConstruct chạy ở bước 5, còn proxy chỉ được tạo ở bước 7. Thêm nữa đây là gọi nội bộ. Muốn chạy việc có transaction lúc khởi động: dùng @EventListener(ApplicationReadyEvent.class) trong một bean khác, hoặc ApplicationRunner.

// Viết một BeanPostProcessor: đo thời gian khởi tạo, hoặc tự bọc proxy như AOP làm
@Component
class SlowBeanReporter implements BeanPostProcessor {
  private final Map<String, Long> start = new ConcurrentHashMap<>();
  public Object postProcessBeforeInitialization(Object bean, String name) {
    start.put(name, System.nanoTime()); return bean;
  }
  public Object postProcessAfterInitialization(Object bean, String name) {
    long ms = (System.nanoTime() - start.remove(name)) / 1_000_000;
    if (ms > 200) log.warn("Bean {} khởi tạo mất {} ms", name, ms);
    return bean;   // trả về object khác ở đây = thay bean bằng proxy
  }
}

Cấp 1 · singletonObjectsbean hoàn chỉnh

Vì sao cần cấp 3 (factory) mà không chỉ cấp 2?

Nếu A cần AOP proxy, thì thứ B nhận phải là proxy của A, không phải A gốc. Nhưng bình thường proxy chỉ được tạo ở cuối vòng đời (bước BeanPostProcessor after). Factory ở cấp 3 cho phép tạo proxy sớm chỉ khi thật sự có người cần tham chiếu sớm (getEarlyBeanReference), còn bình thường vẫn để AOP tạo proxy đúng lúc.

Cách sửa đúng thay vì bật cờ

  • Thiết kế lại: tách phần dùng chung sang bean thứ ba mà cả hai cùng phụ thuộc.
  • Event: A publish event, B lắng nghe, không ai giữ tham chiếu tới ai.
  • @Lazy trên tham số constructor: Spring tiêm một proxy lười, object thật chỉ tạo lúc dùng lần đầu.
  • Vòng phụ thuộc thường là dấu hiệu hai class đang làm việc của nhau; nói được điều này khi phỏng vấn là ghi điểm.

Chương 06

AOP và proxy

Nền móng của @Transactional, @Async, @Cacheable, @PreAuthorize, @Retryable. Hiểu proxy là hiểu vì sao chúng có lúc không chạy.

Phỏng vấn sẽ hỏi
  • AOP là gì? Aspect, advice, pointcut, join point?
  • JDK dynamic proxy khác CGLIB thế nào? Spring Boot dùng cái nào?
  • Vì sao gọi method nội bộ thì @Transactional không có tác dụng?

Thuật ngữ

  • Aspect: một mối quan tâm cắt ngang (log, transaction, bảo mật), đóng gói thành class.
  • Join point: điểm có thể chèn code vào; trong Spring AOP chỉ là lời gọi method.
  • Pointcut: biểu thức chọn join point, ví dụ @annotation(Timed).
  • Advice: code chèn vào: @Before, @AfterReturning, @AfterThrowing, @After, @Around.
  • Weaving: ghép aspect vào code. Spring AOP ghép lúc chạy bằng proxy; AspectJ ghép lúc biên dịch hoặc lúc nạp class.

Ví dụ: đo thời gian mọi method có @Timed

@Aspect @Component
class TimingAspect {
  @Around("@annotation(timed)")
  Object time(ProceedingJoinPoint pjp, Timed timed) throws Throwable {
    long t0 = System.nanoTime();
    try {
      return pjp.proceed();        // gọi method thật
    } finally {
      log.info("{} mất {} ms", pjp.getSignature().toShortString(),
               (System.nanoTime() - t0) / 1_000_000);
    }
  }
}

Chương 07

@Transactional chuyên sâu

Chương quan trọng nhất của sổ tay. Gần như chắc chắn bị hỏi, và là nơi phân biệt người đã debug lỗi transaction thật với người chỉ đọc tài liệu.

Phỏng vấn sẽ hỏi
  • @Transactional hoạt động thế nào bên dưới?
  • Exception nào thì rollback? Checked exception thì sao?
  • Kể các trường hợp @Transactional không có tác dụng.
  • Propagation REQUIRED, REQUIRES_NEW, NESTED khác nhau thế nào?
  • readOnly = true có tác dụng gì?

Bên dưới một lời gọi @Transactional

1Controller gọi orderService.placeOrder(), thật ra là gọi proxy
2Proxy chuyển cho TransactionInterceptor, đọc thuộc tính: propagation, isolation, timeout, readOnly, rollbackFor
3PlatformTransactionManager.getTransaction() (với JPA là JpaTransactionManager): lấy connection từ HikariCP, setAutoCommit(false)
4Gắn connection và EntityManager vào ThreadLocal (TransactionSynchronizationManager); mọi repository trong cùng thread tự dùng chung connection này
5Gọi method thật
6Không lỗi → commit() (Hibernate flush trước). Lỗi → xét luật rollback → rollback() hoặc vẫn commit()
7Gỡ khỏi ThreadLocal, trả connection về pool, chạy callback afterCommit

Bước 4 giải thích nhiều bẫy cùng lúc: transaction gắn với thread, nên code chạy ở thread khác (@Async, CompletableFuture, parallelStream) nằm ngoài transaction.

@RestControllerAdvice
class ApiErrors {
  @ExceptionHandler(MethodArgumentNotValidException.class)
  ProblemDetail invalid(MethodArgumentNotValidException e) {
    ProblemDetail p = ProblemDetail.forStatus(400);
    p.setTitle("Dữ liệu không hợp lệ");
    p.setProperty("errors", e.getFieldErrors().stream()
        .collect(toMap(FieldError::getField, FieldError::getDefaultMessage, (a, b) -> a)));
    return p;
  }
  @ExceptionHandler(SlotUnavailableException.class)
  ProblemDetail conflict(SlotUnavailableException e) { return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, e.getMessage()); }

  @ExceptionHandler(Exception.class)
  ProblemDetail unknown(Exception e) {
    log.error("Unhandled", e);                         // log đầy đủ ở server
    return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "Đã có lỗi, vui lòng thử lại"); // không lộ chi tiết
  }
}

      @Valid và @Validated

      • @Valid (Jakarta): kiểm tra object, đi sâu vào object con. Dùng trên tham số controller.
      • @Validated (Spring): hỗ trợ nhóm ràng buộc (ví dụ OnCreate, OnUpdate), và đặt trên class để bật kiểm tra tham số method của service (@Validated class + @NotNull tham số), lỗi là ConstraintViolationException.
      • Lỗi validation của @RequestBody là MethodArgumentNotValidException; của @RequestParam/@PathVariable (Boot 3.2+) là HandlerMethodValidationException.

      Thứ tự tìm handler lỗi

      1. @ExceptionHandler trong chính controller.
      2. @ControllerAdvice (có thể nhiều, dùng @Order), chọn handler khớp kiểu exception gần nhất.
      3. ResponseStatusException / @ResponseStatus trên class exception.
      4. Không ai xử lý: Spring Boot chuyển tới /error (BasicErrorController).

      Lỗi xảy ra trong filter (ví dụ Spring Security từ chối) không đi qua DispatcherServlet nên không tới @ControllerAdvice; xử lý bằng AuthenticationEntryPoint / AccessDeniedHandler của Security.
