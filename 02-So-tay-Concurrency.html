Bản đồ và cách học

Mọi lỗi đa luồng đều quy về ba vấn đề gốc. Hiểu ba vấn đề này thì mọi công cụ phía sau chỉ là cách giải chúng.

Vấn đề 1

Tính nguyên tử

Một thao tác nhìn như một bước (count++) thật ra gồm nhiều bước. Thread khác chen vào giữa thì kết quả sai.

Vấn đề 2

Thread A đã ghi, nhưng thread B vẫn đọc giá trị cũ trong cache của CPU hoặc thanh ghi, có khi đọc giá trị cũ mãi mãi.

Giải bằng: volatile, synchronized, happens-before

Chương 01

Thread và vòng đời của nó

Bấm các hành động bên dưới để xem thread chuyển trạng thái thế nào. Đây đúng là các trạng thái bạn sẽ đọc trong thread dump.

Phỏng vấn sẽ hỏi
  • Process và thread khác nhau thế nào? Concurrency khác parallelism ra sao?
  • Thread có những trạng thái nào? BLOCKED khác WAITING ở đâu?
  • Gọi run() khác gọi start() thế nào? sleep() khác wait() thế nào?

ĐO THẬT

Bốn thread, bốn trạng thái

holder    -> TIMED_WAITING  // đang giữ khoá và sleep(3000)
doi-khoa  -> BLOCKED        // chờ vào synchronized bị holder giữ
dang-wait -> WAITING        // gọi wait()
dang-park -> WAITING        // LockSupport.park(), cách ReentrantLock chờ

Chi tiết hay bị hỏi: thread chờ synchronized có trạng thái BLOCKED, còn thread chờ ReentrantLock lại là WAITING, vì ReentrantLock dùng LockSupport.park() bên dưới.

Những điều cơ bản phải chắc

  • Process có không gian bộ nhớ riêng. Thread là luồng chạy bên trong process, các thread chia sẻ heap nhưng mỗi thread có stack riêng.
  • Concurrency: nhiều việc tiến triển xen kẽ (có thể chỉ 1 CPU). Parallelism: nhiều việc chạy cùng lúc thật trên nhiều CPU.
  • Mỗi Thread thông thường (platform thread) ứng với một thread của hệ điều hành, tốn khoảng 1 MB stack và chi phí chuyển ngữ cảnh. Vì vậy không thể tạo hàng trăm nghìn cái.
  • t.run() chỉ là gọi hàm bình thường trên thread hiện tại. t.start() mới tạo thread mới. Gọi start() hai lần ném IllegalThreadStateException.
  • sleep() giữ nguyên khoá đang cầm. wait() nhả khoá và chờ được đánh thức.

Dừng một thread đúng cách: interrupt

Java không có cách giết thread an toàn (Thread.stop() đã bị loại bỏ). Cách đúng là interrupt: gửi tín hiệu "hãy dừng", và code trong thread tự kiểm tra rồi dừng.

while (!Thread.currentThread().isInterrupted()) {
    try {
        processNextBatch();
        Thread.sleep(1000);
    } catch (InterruptedException e) {
        // sleep/wait ném lỗi này và XOÁ cờ interrupt; phải đặt lại để vòng lặp thấy
        Thread.currentThread().interrupt();
    }
}
Lỗi rất phổ biếncatch (InterruptedException e) {} nuốt mất tín hiệu dừng. Kết quả: executor.shutdownNow() không dừng được task, ứng dụng tắt chậm hoặc treo khi deploy.

Check-then-act: dạng race condition hay gặp nhất trong code nghiệp vụ

Kiểm tra một điều kiện rồi hành động dựa trên nó, trong khi thread khác có thể làm điều kiện đó thay đổi ở giữa. Chính là lỗi đặt trùng chỗ, trừ điểm hai lần mà bạn đã luyện ở phần phỏng vấn trước.

// Sai: hai thread cùng thấy "chưa có", cùng tạo
if (!cache.containsKey(id)) {
    cache.put(id, loadFromDb(id));
}
// Đúng: một thao tác nguyên tử
cache.computeIfAbsent(id, k -> loadFromDb(k));

// Ở tầng DB cũng vậy: SELECT kiểm tra rồi INSERT là check-then-act
// → dùng unique constraint, SELECT ... FOR UPDATE, hoặc UPDATE ... WHERE điều kiện

Hình động: giá trị mới bị kẹt ở core khác

Chấm xanh là một lần đọc hoặc ghi đi qua bộ nhớ chính. Không có volatile, worker chỉ đọc bộ nhớ đúng một lần lúc bắt đầu (JIT đưa giá trị vào thanh ghi), sau đó quay vòng trên thanh ghi nên không bao giờ thấy giá trị mới, giống hệt số đo thật ở trên.

Happens-before: luật "nếu A xảy ra trước B thì B thấy mọi thứ A đã ghi"

  • Trong một thread: lệnh trước happens-before lệnh sau.
  • Khoá: nhả khoá (ra khỏi synchronized, unlock()) happens-before lần lấy cùng khoá đó tiếp theo.
  • volatile: ghi vào biến volatile happens-before mọi lần đọc biến đó sau đó.
  • Thread: t.start() happens-before mọi lệnh trong t; mọi lệnh trong t happens-before khi t.join() trả về.
  • Executor, Future: việc submit task happens-before lúc task chạy; task chạy xong happens-before future.get() trả về.
  • final: field final được ghi xong trong constructor thì thread nào thấy object cũng thấy giá trị đúng.
  • Bắc cầu: A trước B, B trước C thì A trước C.

Vì có luật bắc cầu, volatile còn "kéo theo" các biến thường: mọi thứ thread A ghi trước khi ghi biến volatile đều được thread B thấy sau khi đọc biến volatile đó.

Double-checked locking và đảo thứ tự lệnh

instance = new Singleton() gồm ba bước: (1) cấp bộ nhớ, (2) chạy constructor, (3) gán địa chỉ cho instance. CPU và JIT được đảo thành 1 → 3 → 2. Thread khác thấy instance != null ở bước 3 và dùng một object chưa khởi tạo xong.

public final class Config {
    private static volatile Config instance;   // thiếu volatile là sai
    public static Config get() {
        Config c = instance;
        if (c == null) {
            synchronized (Config.class) {
                c = instance;
                if (c == null) instance = c = new Config();
            }
        }
        return c;
    }
}
// Cách gọn hơn và an toàn: holder idiom, JVM đảm bảo nạp class chỉ một lần
private static class Holder { static final Config I = new Config(); }
public static Config get() { return Holder.I; }
// Trong Spring: để container quản lý bean singleton, không cần tự viết
Chương 04

synchronized, wait và notify

Công cụ đồng bộ đầu tiên của Java. Đơn giản, đủ dùng cho phần lớn trường hợp, và được JVM tối ưu rất tốt.

Phỏng vấn sẽ hỏi
  • synchronized khoá cái gì? Method static khác method thường ra sao?
  • Reentrant là gì?
  • Vì sao wait() phải nằm trong vòng while?

Khoá cái gì?

synchronized void a() {}         // khoá this
static synchronized void b() {}  // khoá OrderService.class
synchronized (lock) { ... }      // khoá object lock

// Nên: khoá riêng, không ai bên ngoài lấy được
private final Object lock = new Object();

Mỗi object Java đều có một monitor. Hai method synchronized thường trên cùng một object không chạy song song được, nhưng method static và method thường thì được, vì chúng khoá hai thứ khác nhau.

Đừng khoá trên String hằng, Integer hoặc object có thể bị đổi (field không final): hai chỗ code khác nhau có thể vô tình dùng chung một khoá.

Reentrant và cách JVM tối ưu

Reentrant: thread đang giữ khoá có thể vào lại chính khoá đó (gọi một method synchronized khác của cùng object) mà không tự khoá chết mình. JVM đếm số lần vào và chỉ nhả khi ra hết.

Khi không ai tranh chấp, JVM khoá bằng một phép CAS trên mark word của object header (khoá nhẹ). Khi có tranh chấp thật, khoá "phình" thành monitor của hệ điều hành, thread phải ngủ và được đánh thức.

Biased locking (tối ưu cũ cho trường hợp chỉ một thread dùng khoá) bị tắt mặc định từ Java 15 và bị gỡ ở Java 18. Tài liệu cũ hay nhắc, đừng nói nó là hành vi hiện tại.

wait / notify: hàng đợi người sản xuất – người tiêu dùng

class BoundedBuffer<T> {
    private final Deque<T> items = new ArrayDeque<>();
    private final int cap = 10;

    synchronized void put(T x) throws InterruptedException {
        while (items.size() == cap) wait();   // nhả khoá, ngủ chờ
        items.addLast(x);
        notifyAll();                          // đánh thức người đang chờ lấy
    }
    synchronized T take() throws InterruptedException {
        while (items.isEmpty()) wait();
        T x = items.removeFirst();
        notifyAll();
        return x;
    }
}
// Thực tế: dùng luôn ArrayBlockingQueue, đã có sẵn put()/take()
Phải giữ khoáGọi wait()/notify() ngoài synchronized của chính object đó ném IllegalMonitorStateException.
Phải dùng whileThread có thể tỉnh dậy mà không ai gọi notify (spurious wakeup), hoặc thread khác đã lấy mất phần tử trước. Luôn kiểm tra lại điều kiện.
Ưu tiên notifyAllnotify() chỉ đánh thức một thread ngẫu nhiên, có thể đánh thức nhầm loại (người sản xuất thay vì người tiêu dùng) và cả hệ thống đứng.

private final ReentrantLock lock = new ReentrantLock();

boolean transfer(Account from, Account to, long amount) throws InterruptedException {
    if (!lock.tryLock(2, TimeUnit.SECONDS)) {
        return false;              // không chờ mãi: báo bận, để client thử lại
    }
    try {
        from.debit(amount);
        to.credit(amount);
        return true;
    } finally {
        lock.unlock();              // bắt buộc trong finally
    }
}

ReadWriteLock và StampedLock

ReentrantReadWriteLock: nhiều thread đọc cùng lúc, nhưng ghi thì độc quyền. Hợp với dữ liệu đọc rất nhiều, ghi rất ít (cấu hình, bảng giá).

StampedLock (Java 8): thêm chế độ đọc lạc quan, không khoá gì cả, đọc xong kiểm tra "có ai ghi trong lúc mình đọc không" bằng validate(stamp); có thì đọc lại bằng khoá thật. Nhanh hơn nhưng không reentrant, dễ dùng sai.

AQS: bộ khung bên dưới

AbstractQueuedSynchronizer là nền của ReentrantLock, Semaphore, CountDownLatch, ReentrantReadWriteLock. Nó gồm:

  • Một số nguyên state được cập nhật bằng CAS (với lock: 0 là trống, n là số lần vào lại).
  • Một hàng đợi các thread đang chờ (biến thể của CLH queue).
  • Thread không lấy được thì vào hàng đợi và LockSupport.park(); người nhả khoá unpark() thread đầu hàng.

Nói được "ReentrantLock dùng AQS, state đếm số lần vào lại, thread chờ được park trong hàng đợi" là câu trả lời ở mức senior.

Chương 06

CAS, Atomic và LongAdder

Đồng bộ không cần khoá: thay vì "chặn người khác lại", ta "thử ghi, nếu có người chen vào thì thử lại".

Phỏng vấn sẽ hỏi
  • CAS là gì? AtomicInteger hoạt động thế nào?
  • Vấn đề ABA là gì?
  • Vì sao LongAdder nhanh hơn AtomicLong?

Compare-And-Swap là một lệnh của CPU (trên x86 là LOCK CMPXCHG): "nếu giá trị ở địa chỉ này đang là expected thì đổi thành new, trả về thành công; nếu không thì không làm gì, trả về thất bại". Cả bước so sánh và ghi diễn ra nguyên tử trong phần cứng.

// Bên trong AtomicInteger.incrementAndGet(), viết lại cho dễ hiểu
int incrementAndGet() {
    while (true) {
        int expected = value;              // 1. đọc (value là volatile)
        int next = expected + 1;           // 2. tính
        if (compareAndSet(expected, next))  // 3. ghi nếu chưa ai chen vào
            return next;
        // thất bại: có thread khác vừa ghi, quay lại đọc giá trị mới
    }
}

Thử chế độ "AtomicInteger (CAS)" trong mô phỏng ở chương 02: khi hai thread xen kẽ, thread ghi sau sẽ CAS thất bại và tự thử lại, không mất lần cộng nào.

Vấn đề ABA

Thread 1 đọc giá trị A. Trong lúc đó thread 2 đổi A → B → A. Thread 1 CAS thấy vẫn là A, tưởng không ai đụng vào. Với bộ đếm thì không sao, nhưng với cấu trúc liên kết (stack, queue không khoá) thì có thể hỏng dữ liệu.

Cách xử lý: gắn thêm số phiên bản, AtomicStampedReference so sánh cả giá trị lẫn stamp. Đây cũng chính là ý tưởng của optimistic locking với cột @Version trong JPA.

LongAdder: chia để giảm tranh chấp

base4cell[0]7cell[1]5cell[2]6
sum() = 4 + 7 + 5 + 6 = 22

Tranh chấp cao thì CAS thất bại liên tục, mọi thread quay vòng thử lại trên cùng một biến. LongAdder rải các lần cộng ra nhiều ô, mỗi thread cộng vào ô của mình, sum() cộng tất cả lại. Đổi lại sum() không phải ảnh chụp chính xác tại một thời điểm.

Mỗi ô được đệm cho nằm trên cache line riêng (@Contended) để tránh false sharing: hai biến khác nhau nằm cùng một cache line 64 byte khiến các core tranh nhau dù không dùng chung dữ liệu.

Hình động: 4 thread cùng cộng 5 lần

0CAS thành công
0CAS thất bại, phải thử lại
0Nhịp

Mỗi nhịp, mọi thread chưa xong cùng đọc rồi cùng CAS. Với một ô duy nhất, chỉ thread đầu tiên thắng, các thread còn lại thất bại và quay vòng. LongAdder thật bắt đầu bằng một ô base và chỉ tách thêm ô khi phát hiện tranh chấp; ở đây vẽ sẵn 4 ô cho dễ thấy.

Chọn gìBộ đếm chỉ để thống kê, nhiều thread cộng (số request, số lượt xem): LongAdder. Cần giá trị chính xác ngay sau khi tăng (cấp số thứ tự, id): AtomicLong. Cập nhật một object theo giá trị cũ: AtomicReference.updateAndGet.

Hàng nghìn phần tử biến mất mà không có exception nào. Hai thread cùng ghi vào một bucket, hoặc một thread đang resize mảng trong khi thread khác ghi. Ở Java 7, resize đồng thời còn có thể tạo vòng lặp trong danh sách liên kết, làm get() chạy mãi với CPU 100%.

ĐO THẬT

Từng thao tác get, put an toàn, nhưng ghép hai thao tác thì không. Dùng các method nguyên tử: merge, compute, computeIfAbsent, putIfAbsent.

ConcurrentHashMap bên trong (Java 8 trở đi)

  • Đọc không khoá: mảng bucket và giá trị trong node là volatile, nên get() không cần khoá.
  • Ghi vào bucket trống: dùng CAS đặt node đầu tiên, không khoá.
  • Ghi vào bucket đã có phần tử: synchronized trên node đầu của riêng bucket đó. Hai thread ghi vào hai bucket khác nhau chạy song song hoàn toàn.
  • Bucket dài: từ 8 phần tử trở lên (và mảng có từ 64 bucket) thì chuyển thành cây đỏ đen, tìm kiếm O(log n) thay vì O(n).
  • Resize: nhiều thread cùng giúp chuyển dữ liệu sang mảng mới.
  • size(): đếm bằng cơ chế giống LongAdder nên có thể không chính xác tuyệt đối khi đang có ghi đồng thời.
  • Java 7 dùng cách khác: chia thành 16 segment, mỗi segment một ReentrantLock. Nếu interviewer hỏi "segment", hãy nói đó là cách cũ.

Vì sao cấm null? Với map đồng thời, get(k) trả về null thì không phân biệt được "không có key" hay "key có giá trị null", và cũng không thể kiểm tra lại bằng containsKey vì trạng thái có thể đổi giữa hai lần gọi.

Chọn số thread

  • Việc tính toán (CPU-bound): khoảng bằng số core (hoặc core + 1). Nhiều hơn chỉ tốn chuyển ngữ cảnh.
  • Việc chờ I/O (gọi DB, HTTP): số core × (1 + thời gian chờ / thời gian tính). Ví dụ 2 core, mỗi request chờ DB 90 ms và tính 10 ms: 2 × (1 + 9) = 20 thread.
  • Công thức chỉ là điểm bắt đầu. Đo bằng K6, nhìn CPU, độ trễ, hàng đợi rồi chỉnh. Và nhớ giới hạn phía sau: 50 thread mà connection pool DB chỉ có 10 thì 40 thread đứng chờ.

Bốn chính sách khi đầy

  • AbortPolicy (mặc định): ném RejectedExecutionException. Rõ ràng, nên dùng cho API để trả 503/429.
  • CallerRunsPolicy: thread gửi task tự chạy luôn task đó. Tự nhiên làm chậm phía gửi (back-pressure). Hợp với job nội bộ.
  • DiscardPolicy: lặng lẽ bỏ. Nguy hiểm, mất dữ liệu không ai biết.
  • DiscardOldestPolicy: bỏ task cũ nhất trong hàng đợi để nhận task mới.
execute() và submit() xử lý exception khác nhauexecute(task): exception được in ra (qua UncaughtExceptionHandler) và thread đó chết, pool tạo thread mới. submit(task): exception bị gói vào Future; nếu không ai gọi future.get() thì lỗi biến mất hoàn toàn, không có dòng log nào. Đây là lý do nhiều job "chạy mà không làm gì, không báo lỗi".

Virtual thread (Java 21)

Thay đổi lớn nhất của concurrency Java trong mười năm. Viết code chặn (blocking) bình thường nhưng chịu tải như code bất đồng bộ.

Phỏng vấn sẽ hỏi
  • Virtual thread là gì, khác platform thread thế nào?
  • Pinning là gì?
  • Khi nào không nên dùng virtual thread?

Cách hoạt động

Platform thread = 1 thread hệ điều hành, stack cố định khoảng 1 MB, tạo vài nghìn là hết sức. Virtual thread do JVM quản lý, stack lưu dạng object trên heap và co giãn, tạo hàng triệu cái được.

Virtual thread chạy "cõng" trên một số ít carrier thread (một ForkJoinPool, mặc định số thread = số CPU). Khi virtual thread gặp thao tác chặn (đọc socket, sleep, chờ lock), JVM tháo nó khỏi carrier, cất stack lên heap, và carrier đi chạy virtual thread khác. Xong I/O thì gắn lại.

Mô hình M:N: hàng triệu virtual thread trên vài carrier, giống goroutine của Go.

ĐO THẬT
10 000 task, mỗi task chờ I/O 100 ms

mili giây trên máy 2 vCPU

Pool 200 thread phải chạy 50 đợt × 100 ms ≈ 5 giây. Virtual thread chạy cả 10 000 cùng lúc, xong trong 0,24 giây, nhanh hơn khoảng 21 lần.

Chặn bên trong synchronized (ở Java 21–23) hoặc trong code native thì virtual thread không tháo ra được, giữ luôn carrier. Vài chỗ như vậy cùng lúc là hết carrier, cả hệ thống đứng. Cách xử lý ở Java 21: đổi synchronized quanh I/O thành ReentrantLock. Java 24 (JEP 491) đã sửa trường hợp synchronized.

Nên dùng

  • Web service phần lớn thời gian chờ DB, HTTP, Redis.
  • Spring Boot 3.2+: spring.threads.virtual.enabled=true, Tomcat và @Async chạy trên virtual thread.
  • Thay cho code reactive phức tạp khi chỉ cần chịu tải I/O cao.

Không nên hoặc cần cẩn thận

  • Việc tính toán nặng CPU: không nhanh hơn, vì số CPU không đổi.
  • Không gom virtual thread vào pool: chúng rẻ, tạo mới cho mỗi task.
  • Phải tự giới hạn tài nguyên phía sau: 10 000 virtual thread cùng lao vào DB có 10 connection. Dùng Semaphore hoặc dựa vào connection pool.
  • ThreadLocal chứa dữ liệu lớn: nhân lên hàng triệu bản. Java 21 có Scoped Values (preview) thay thế.

CountDownLatch, Semaphore, CyclicBarrier

Các công cụ phối hợp nhiều thread. Mỗi cái giải đúng một kiểu bài toán.

CountDownLatch

Chờ N việc xong rồi mới đi tiếp. Dùng một lần, không đặt lại được.

var done = new CountDownLatch(3);
// mỗi worker xong:
done.countDown();
// main chờ:
done.await(5, SECONDS);

Ví dụ: chờ 3 cache nạp xong mới mở cổng nhận traffic. Rất hay dùng trong test đa luồng.

Semaphore

Giới hạn tối đa N thread cùng làm một việc.

var slots = new Semaphore(5);
slots.acquire();
try { callPartnerApi(); }
finally { slots.release(); }

Ví dụ: API đối tác chỉ cho 5 kết nối đồng thời; giới hạn virtual thread vào một tài nguyên.

CyclicBarrier

N thread đợi nhau tại một điểm rồi cùng đi tiếp. Dùng lại được nhiều vòng.

var b = new CyclicBarrier(4,
  () -> mergeResults());
// mỗi thread:
computePart(); b.await();

Ví dụ: chia dữ liệu thành 4 phần xử lý song song, đủ 4 phần mới gộp. Phaser là bản linh hoạt hơn.

Deadlock, livelock, starvation

Ba kiểu hệ thống "sống nhưng không tiến lên được".

Phỏng vấn sẽ hỏi
  • Điều kiện để xảy ra deadlock? Cách phòng tránh?
  • Phát hiện deadlock trên production thế nào?
  • Livelock khác deadlock ra sao?
ĐO THẬT

Hai giao dịch chuyển tiền ngược chiều nhau

// thread 1: transfer(A, B) → khoá A rồi khoá B
// thread 2: transfer(B, A) → khoá B rồi khoá A
$ jstack <pid>
Found one Java-level deadlock:
"transfer-A-to-B":
  waiting to lock monitor ... which is held by "transfer-B-to-A"
"transfer-B-to-A":
  waiting to lock monitor ... which is held by "transfer-A-to-B"
	at Deadlock.transfer(Deadlock.java:11)
Found 1 deadlock.

Hình động: hai thread chuyển tiền ngược chiều

Đường liền: thread đang giữ khoá. Đường đứt chạy: thread đang chờ khoá. Khi hai đường chờ tạo thành vòng tròn là deadlock.

Bốn điều kiện (Coffman), phá một là hết

  1. Độc quyền: tài nguyên chỉ một người giữ.
  2. Giữ và chờ: giữ cái này trong khi chờ cái kia.
  3. Không cướp được: không ai lấy khoá từ tay người đang giữ.
  4. Chờ vòng tròn: A chờ B, B chờ A.

Cách phá thực tế nhất là điều kiện 4: luôn khoá theo cùng một thứ tự.

Account first  = a.id() < b.id() ? a : b;
Account second = a.id() < b.id() ? b : a;
synchronized (first) { synchronized (second) { ... } }

Hoặc phá điều kiện 3 bằng tryLock(timeout): chờ quá lâu thì nhả hết và thử lại.

Họ hàng của deadlock

  • Livelock: các thread không bị chặn mà liên tục nhường nhau, ví dụ cùng tryLock thất bại, cùng nhả, cùng thử lại đúng lúc. Sửa bằng thời gian chờ ngẫu nhiên trước khi thử lại.
  • Starvation: một thread mãi không được chạy vì thread khác luôn giành trước (khoá không công bằng, ưu tiên thấp). Fair lock giảm được nhưng chậm hơn.
  • Deadlock ở tầng DB: hai transaction khoá các dòng ngược thứ tự. MySQL tự phát hiện và huỷ một bên với lỗi Deadlock found when trying to get lock. Xem bằng SHOW ENGINE INNODB STATUS; sửa bằng cách cập nhật dòng theo thứ tự id cố định, giữ transaction ngắn, và cho phép thử lại.
  • Thread pool tự khoá: task trong pool submit task con vào chính pool đó rồi chờ kết quả. Pool đầy thì task cha chờ task con, task con chờ chỗ trống mãi.

Concurrency trong Spring Boot

Bạn ít khi tự tạo thread trong Spring Boot, nhưng mỗi request đã là một thread. Đây là những lỗi thật hay gặp nhất.

ĐO THẬT

1. Bean singleton giữ trạng thái trong field

@Service  // chỉ có MỘT instance cho mọi request
class GreetingService {
    private String currentUser;             // lỗi: dữ liệu của request nằm trong field
    String greet(String user) { currentUser = user; work(); return "Xin chao " + currentUser; }
}
// 2 thread, mỗi thread 100 000 lần, một thread chào "An", một thread chào "Binh"
so lan chao nham nguoi: 171384 / 200000

Hơn 85% lần chào nhầm người. Trong ứng dụng thật, đây là lỗi lộ dữ liệu người dùng này cho người dùng khác, và thường chỉ xuất hiện khi có tải. Bean singleton phải không có trạng thái: dữ liệu của request đi qua tham số và biến cục bộ.

ĐO THẬT

2. ThreadLocal không được dọn trong thread pool

request 1 cua loc: user=loc@rikkei
request 2 cua khach an danh: user=loc@rikkei  <- du lieu cua request truoc

Thread của Tomcat được dùng lại. Luôn remove() trong finally (xem chương 12 của sổ tay JVM). Spring Security cũng lưu SecurityContext trong ThreadLocal, nên code chạy ở thread khác (@Async, CompletableFuture) không có thông tin đăng nhập trừ khi dùng DelegatingSecurityContextExecutor.

3. @Async

  • Cần @EnableAsync. Gọi method @Async từ chính class đó thì không chạy bất đồng bộ, vì Spring dùng proxy và lời gọi nội bộ không đi qua proxy.
  • Pool mặc định của Spring Boot: 8 thread core, hàng đợi không giới hạn. Cấu hình spring.task.execution.pool.queue-capacity và max-size.
  • Method trả về void mà ném exception thì lỗi chỉ đi tới AsyncUncaughtExceptionHandler; không cấu hình là mất. Trả về CompletableFuture nếu cần biết kết quả.

4. @Transactional và thread

Transaction của Spring gắn với thread hiện tại (lưu trong ThreadLocal của TransactionSynchronizationManager). Code chạy trong @Async hay CompletableFuture nằm ngoài transaction của method gọi nó, không thấy dữ liệu chưa commit, và không rollback cùng.

@Transactional
public void placeOrder(Order o) {
    repo.save(o);
    // sai: email có thể gửi trước khi commit, hoặc order rollback mà email đã đi
    mailService.sendAsync(o);
}
// đúng: chạy sau khi commit thành công
@TransactionalEventListener(phase = AFTER_COMMIT)
void onPlaced(OrderPlaced e) { mailService.send(e.order()); }

5. @Scheduled chỉ có một thread

Mặc định Spring Boot dùng scheduler 1 thread (spring.task.scheduling.pool.size=1). Một job chạy lâu (ví dụ job gửi mail điểm thưởng) sẽ làm mọi job khác bị trễ theo. Tăng pool size, hoặc tách job nặng sang executor riêng.

6. Nhiều instance thì khoá trong JVM vô dụng

synchronized, ReentrantLock, ConcurrentHashMap chỉ có tác dụng trong một JVM. Chạy 3 task ECS sau load balancer là 3 JVM độc lập. Đồng bộ giữa các instance phải dùng thứ dùng chung:

  • Database: SELECT ... FOR UPDATE, unique constraint, @Version.
  • Redis: SET key value NX PX, Redisson.
  • Job định kỳ: ShedLock, hoặc chạy bằng ECS Scheduled Task như dự án của bạn.
Nối với dự án của bạnKhi được hỏi "bạn đã xử lý vấn đề đồng thời nào", các điểm có thật để kể: job gửi mail điểm chạy bằng ECS Scheduled Task nên không bị nhiều instance cùng chạy, và có cột trạng thái mail để chạy lại không gửi trùng; rate limit dùng Lua script trên Redis vì nhiều instance cần đếm chung và các bước phải nguyên tử; Sorted Set của Redis xử lý ZINCRBY đồng thời mà không cần khoá phía ứng dụng.
