Chương 01

Kiến trúc JVM

JVM là một chương trình C++ đọc bytecode và biến nó thành lệnh máy. Nó có ba khối lớn.

Phỏng vấn sẽ hỏi
  • JDK, JRE, JVM khác nhau thế nào?
  • Vì sao Java "viết một lần, chạy mọi nơi"?
  • Class được nạp vào JVM ra sao?
OrderService.java→ javac →OrderService.class (bytecode)→ JVM →lệnh máy x86 / ARM

1. Class Loader Subsystem

Loading đọc file .class. Linking kiểm tra bytecode, cấp chỗ cho biến static, nối tham chiếu. Initialization chạy khối static {}.

Ba loader theo cha-con: Bootstrap → Platform → Application. Cơ chế parent delegation: hỏi cha trước, nên không ai tự viết đè được java.lang.String.

2. Runtime Data Areas

Bộ nhớ khi chạy: Heap, Metaspace, Code cache dùng chung; mỗi thread có Stack, PC register, Native stack riêng. Chương 02 đi sâu.

3. Execution Engine

Interpreter chạy từng lệnh bytecode, khởi động nhanh nhưng chậm. JIT (C1, C2) dịch đoạn code chạy nhiều thành lệnh máy tối ưu. Garbage Collector dọn heap.

JDK = JRE + công cụ phát triển (javac, jcmd, jstack, jmap, jfr). JRE = JVM + thư viện chuẩn. Từ Java 11 không còn bản JRE riêng; người ta dùng JDK hoặc tự đóng gói runtime gọn bằng jlink.

"Viết một lần chạy mọi nơi" vì javac chỉ tạo bytecode trung gian; mỗi hệ điều hành có JVM riêng dịch bytecode đó thành lệnh máy.

Lưu ý cho production: image Docker nên dùng JDK đầy đủ (hoặc ít nhất có jcmd), vì khi có sự cố bạn cần công cụ để lấy heap dump, thread dump ngay trong container. Image chỉ có JRE tối giản sẽ khiến bạn "mù" lúc cần nhất.

PermGen → Metaspace (Java 8)

Trước Java 8, thông tin class nằm trong PermGen, một phần của heap có kích thước cố định, rất hay gặp OutOfMemoryError: PermGen space khi redeploy ứng dụng nhiều lần. Java 8 bỏ PermGen, chuyển sang Metaspace nằm ở bộ nhớ native và tự giãn. Đổi lại, nếu có rò rỉ class (ClassLoader leak) thì Metaspace phình mãi, nên trên production vẫn nên đặt MaxMetaspaceSize.

Câu bẫy kinh điển

String a = "loc";              // lấy từ String pool
String b = "loc";              // cùng object trong pool
String c = new String("loc");  // object MỚI trên heap
a == b      // true  : cùng tham chiếu
a == c      // false : khác object
a == c.intern() // true : intern() trả về bản trong pool

Một object nặng bao nhiêu byte

Hiểu chương này để đọc được heap dump và giải thích vì sao List<Integer> tốn bộ nhớ gấp nhiều lần int[].

Trên JVM 64-bit với heap dưới 32 GB (mặc định bật compressed oops), mỗi object gồm:

Object luôn được làm tròn lên bội số của 8 byte. Mark word chứa tuổi GC chỉ dùng 4 bit, nên một object sống sót tối đa 15 lần Minor GC trước khi bắt buộc lên Old. Đó là lý do MaxTenuringThreshold tối đa là 15.

Chương 04

Garbage Collection hoạt động thế nào

GC không tìm rác. Nó tìm những gì còn sống, mọi thứ còn lại là rác.

Phỏng vấn sẽ hỏi
  • GC biết object nào là rác bằng cách nào? GC roots gồm những gì?
  • Vì sao chia Young và Old? Minor, Major, Full GC khác nhau ra sao?
  • Stop-the-world là gì? Vì sao có GC rồi mà Java vẫn bị memory leak?

1. Reachability: đi từ GC roots

GC bắt đầu từ các GC roots rồi lần theo mọi tham chiếu. Object nào không có đường đi tới là rác.

  • Biến cục bộ và tham số trên stack của các thread đang chạy
  • Biến static của các class đã nạp
  • Monitor đang bị synchronized giữ
  • Tham chiếu từ JNI, thread đang sống

Java không đếm tham chiếu (reference counting), nên hai object trỏ vòng vào nhau mà không ai từ root trỏ tới vẫn bị dọn bình thường.

2. Ba kiểu dọn

  • Mark–Sweep: đánh dấu object sống, xoá phần còn lại. Nhanh nhưng để lại lỗ hổng (phân mảnh).
  • Mark–Compact: đánh dấu rồi dồn object sống về một phía. Hết phân mảnh nhưng tốn thời gian di chuyển. Dùng cho Old.
  • Copying: copy object sống sang vùng trống, bỏ nguyên vùng cũ. Chi phí tỉ lệ với số object sống, không phụ thuộc lượng rác. Dùng cho Young.

3. Giả thuyết thế hệ (generational hypothesis)

Quan sát thực tế: phần lớn object chết rất trẻ (DTO của một request, biến tạm trong vòng lặp), số ít sống rất lâu (cache, bean của Spring). Vì vậy heap chia làm hai:

  • Young Generation = Eden + Survivor S0 + Survivor S1. Object mới sinh ở Eden. Dọn thường xuyên bằng copying, rẻ vì đa số đã chết.
  • Old Generation: object sống sót đủ số lần Minor GC (tuổi ≥ MaxTenuringThreshold) được promote lên đây. Dọn ít hơn và đắt hơn.

4. Những chi tiết làm nên tốc độ

  • TLAB (Thread-Local Allocation Buffer): mỗi thread được cấp riêng một mẩu Eden. Cấp phát object chỉ là tăng một con trỏ, không cần khoá, nhanh như cấp phát trên stack trong C.
  • Card table / Remembered set: ghi lại những chỗ Old đang trỏ sang Young, để Minor GC không phải quét toàn bộ Old. Mỗi lần gán tham chiếu, JVM chèn thêm một đoạn code nhỏ gọi là write barrier để cập nhật bảng này.
  • Stop-the-world và safepoint: một số pha GC cần dừng tất cả thread của app. JVM chỉ dừng được thread khi thread chạm tới safepoint (cuối vòng lặp, lời gọi hàm). Một vòng lặp đếm rất dài không có safepoint có thể khiến cả hệ thống chờ (time-to-safepoint).

5. Vì sao có GC vẫn bị memory leak?

GC chỉ dọn object không còn ai tham chiếu. Memory leak trong Java là object vẫn còn được tham chiếu nhưng không bao giờ dùng lại: một static Map làm cache không xoá, listener đăng ký mà không huỷ, ThreadLocal trong thread pool không remove(). Với GC, chúng vẫn "sống".

G1 nhìn từ bên trong

E: EdenS: SurvivorO: OldH: HumongousTrốngĐược chọn dọn trong lần Mixed GC tới
  • Heap chia thành nhiều region bằng nhau (1 đến 32 MB). Máy thật trong thí nghiệm: region size 1024K. Một region có thể là Eden lúc này, lúc khác là Old.
  • Young GC: copy object sống từ các region Eden/Survivor sang region trống.
  • Khi Old chiếm quá ngưỡng (mặc định 45% heap, InitiatingHeapOccupancyPercent), G1 chạy concurrent marking song song với app để biết region Old nào nhiều rác.
  • Sau đó là các lần Mixed GC: dọn Young cộng thêm vài region Old nhiều rác nhất. Đó là nghĩa của chữ "Garbage First".
  • Humongous: object lớn hơn nửa region (ví dụ mảng 600 KB khi region 1 MB) được cấp nguyên các region liền nhau. Tạo nhiều object lớn kiểu này (đọc cả file vào byte[]) dễ gây phân mảnh và Full GC.

Các pha dừng chỉ còn quét root nên rất ngắn. Java 21 có ZGC thế hệ (-XX:+ZGenerational), Java 23 bật mặc định, Java 24 bỏ hẳn bản không thế hệ.
Chương 07

JIT, warm-up và escape analysis

Vì sao request đầu tiên sau khi deploy luôn chậm, và vì sao code Java chạy lâu lại nhanh ngang C++.

Phỏng vấn sẽ hỏi
  • JIT là gì? C1 và C2 khác nhau ra sao?
  • Vì sao app mới khởi động chậm? Xử lý thế nào?
  • Escape analysis là gì?

Tiered compilation (mặc định): code bắt đầu chạy bằng interpreter. Method được gọi vài trăm lần thì C1 biên dịch nhanh, tối ưu nhẹ, kèm đếm thống kê. Gọi tới vài nghìn lần thì C2 biên dịch lại, tối ưu mạnh dựa trên thống kê đã thu: inline method, bỏ kiểm tra thừa, cuộn vòng lặp. Nếu giả định của C2 sai (ví dụ một interface bỗng có class triển khai mới), JVM deoptimize và quay về bản chậm hơn.

ĐO THẬT
Thời gian mỗi lần gọi hàm price() theo thời gian

nano giây / lần gọi, thang log; mỗi đợt 20 000 lần gọi

Xử lý warm-up trên production

  • Cấu hình readiness probe / health check của ECS hoặc load balancer chỉ nhận traffic khi app đã sẵn sàng; có thể tự gọi vài API quan trọng lúc khởi động (warm-up endpoint).

  • Java 21+: CDS / AppCDS giảm thời gian nạp class. Spring Boot 3.3+ hỗ trợ CDS; CRaC và GraalVM native image là lựa chọn mạnh hơn nhưng phức tạp.

JVM trong Docker và ECS

Lỗi phổ biến nhất khi chạy Java trong container: đặt heap bằng đúng RAM của container. Heap chỉ là một phần bộ nhớ JVM dùng.

Phỏng vấn sẽ hỏi
  • Container 2 GB thì đặt -Xmx2g được không?
  • Container bị kill với exit code 137 nghĩa là gì?
  • JVM có biết giới hạn RAM của container không?

Từ Java 10 (và 8u191), JVM đọc giới hạn cgroup của container (UseContainerSupport bật mặc định), nên "RAM" trong mọi phép tính bên dưới là RAM của container, không phải của máy chủ.

ĐO THẬT

Không đặt gì thì task 2 GB chỉ dùng 512 MB heap, lãng phí 75% tiền RAM.

ĐO THẬT

JVM tự đổi GC theo số CPU

Task ECS 1 vCPU (1024 CPU units) sẽ âm thầm chạy Serial GC, mỗi lần GC dừng cả app. Ghi rõ -XX:+UseG1GC nếu muốn G1.

Máy tính ngân sách bộ nhớ

Kéo các thanh để xem tổng bộ nhớ JVM so với giới hạn container. Các con số khác heap là ước lượng cho một Spring Boot API cỡ vừa; đo thật bằng Native Memory Tracking ở bên dưới.

Exit code 137 = bị hệ điều hành giết

137 = 128 + 9 (SIGKILL). Tổng bộ nhớ của tiến trình vượt giới hạn container, kernel OOM killer giết luôn, không có OutOfMemoryError, không có heap dump, log dừng đột ngột. Trên ECS lý do dừng task thường ghi OutOfMemoryError: Container killed due to memory usage.

Phân biệt hai loại:

  • Java OOM: heap đầy, JVM ném OutOfMemoryError, có stack trace và heap dump nếu đã bật cờ.
  • Container OOMKilled: heap có thể còn trống, nhưng heap + phần ngoài heap vượt giới hạn. Cách sửa: giảm MaxRAMPercentage, giảm số thread, hoặc tăng RAM task.

Xử lý sự cố: các quy trình chuẩn

Mỗi sự cố có cùng khung: triệu chứng → lệnh lấy bằng chứng → đọc bằng chứng → nguyên nhân → cách sửa. Log trong chương này là output thật.

SỰ CỐ 1

OutOfMemoryError: Java heap space và memory leak

ĐO THẬT
Heap còn lại sau mỗi lần GC

MB, heap tối đa 128 MB; cùng một ứng dụng, chỉ khác cache có giới hạn hay không

Bản có giới hạn (chỉ giữ 20 000 đơn gần nhất) dao động nhưng luôn quay về đáy khoảng 30 MB. Bản leak không có đáy: mỗi lần GC xong lại cao hơn, đến 12 giây thì đầy 127/128 MB, Full GC liên tục rồi chết.

Quy trình

  1. Xem loại OOM trong log: Java heap space (heap), GC overhead limit exceeded (Parallel GC: hơn 98% thời gian dành cho GC mà thu hồi dưới 2%), Metaspace, Direct buffer memory, unable to create native thread. Mỗi loại một hướng xử lý.
  2. Lấy bằng chứng. Nếu đã bật HeapDumpOnOutOfMemoryError thì có sẵn file. Nếu app còn sống mà heap tăng dần, chụp histogram hai lần cách nhau vài phút để xem class nào tăng:

  3. Mở heap dump bằng Eclipse MAT: báo cáo Leak Suspects, rồi Dominator Tree sắp theo retained size. Chọn object to nhất, dùng "Path to GC Roots" để biết ai đang giữ nó. Ở ví dụ này đường đi là LeakApp.CACHE (static) → HashMap → hàng chục nghìn OrderDto.

Lỗi bộ nhớ hay gặp trong Spring Boot

Đây là chỗ "tối ưu JVM" thật sự diễn ra trong đa số dự án: sửa code, không phải sửa cờ.

1. Load cả bảng vào bộ nhớ

Export CSV, batch gửi mail, báo cáo cuối ngày gọi findAll() trên bảng vài triệu dòng.

// Sai: 2 triệu entity nằm cùng lúc trên heap
List<LogMileage> all = repo.findByDate(yesterday);

// Đúng: đọc từng trang, xử lý xong mới đọc tiếp
Pageable p = PageRequest.of(0, 1000, Sort.by("id"));
Slice<LogMileage> s;
do {
  s = repo.findByDate(yesterday, p);
  process(s.getContent());
  p = s.nextPageable();
} while (s.hasNext());

Bảng rất lớn thì phân trang theo id lớn hơn id cuối (keyset) thay vì OFFSET, vì OFFSET càng về sau càng chậm.

2. Persistence context phình to trong batch

Mọi entity JPA đọc hoặc lưu trong một transaction đều được Hibernate giữ lại (first-level cache) cho tới khi transaction kết thúc.

for (int i = 0; i < orders.size(); i++) {
  em.persist(orders.get(i));
  if (i % 500 == 0) {
    em.flush();   // đẩy xuống DB
    em.clear();   // thả các entity khỏi bộ nhớ
  }
}

Kèm spring.jpa.properties.hibernate.jdbc.batch_size=500 để insert theo lô.

3. Cache không giới hạn

// Sai: lớn mãi, không bao giờ xoá
static final Map<Long, Product> CACHE = new ConcurrentHashMap<>();

// Đúng: Caffeine có giới hạn và hết hạn
Cache<Long, Product> cache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(10))
    .recordStats()
    .build();

Với @Cacheable: spring.cache.caffeine.spec=maximumSize=10000,expireAfterWrite=10m.

4. Hàng đợi vô hạn của thread pool

Executors.newFixedThreadPool(10) dùng LinkedBlockingQueue không giới hạn. Tải tăng đột biến, task xếp hàng trên heap tới khi OOM. Pool mặc định cho @Async của Spring Boot cũng có queue-capacity không giới hạn.

spring.task.execution.pool.core-size=8
spring.task.execution.pool.max-size=16
spring.task.execution.pool.queue-capacity=500

Kèm chính sách khi đầy hàng đợi (CallerRunsPolicy hoặc từ chối có kiểm soát).

5. ThreadLocal trong thread pool

Thread của Tomcat được dùng lại cho request sau. Không xoá thì dữ liệu của request trước (user, tenant) còn nằm đó: vừa leak bộ nhớ, vừa có thể lộ dữ liệu sang người khác.

try {
  CurrentUser.set(user);
  chain.doFilter(req, res);
} finally {
  CurrentUser.remove();   // bắt buộc
}

6. Đọc cả file hoặc response vào bộ nhớ

Files.readAllBytes, MultipartFile.getBytes() với file 200 MB tạo object humongous trong G1. Dùng stream: InputStream đẩy thẳng sang S3 (RequestBody.fromInputStream), StreamingResponseBody khi export.

Cũng như vậy với log: log.debug("data=" + bigObject) vẫn tạo chuỗi lớn kể cả khi tắt debug. Dùng log.debug("data={}", bigObject).

Lab tự làm và cách kể khi phỏng vấn

Cách chắc chắn nhất để trả lời câu "kể một lần bạn tối ưu JVM" là đã thực sự làm. Lab dưới đây mất khoảng hai buổi tối và cho bạn một câu chuyện thật.

Lab: tự gây và tự sửa memory leak trong Spring Boot

  1. Tạo project Spring Boot 3 có Actuator, một API GET /orders/{id} lưu kết quả vào static Map không giới hạn (cố ý gây leak).
  2. Chạy bằng Docker với giới hạn nhỏ: docker run -m 512m -e JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=70 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps -Xlog:gc*:file=/dumps/gc.log" ...
  3. Bắn tải bằng K6 với id ngẫu nhiên. Mở /actuator/metrics/jvm.memory.used theo dõi đáy heap tăng dần.
  4. Chụp jcmd GC.class_histogram hai lần, rồi chờ OOM, lấy heap dump. Mở bằng Eclipse MAT, chụp màn hình Leak Suspects và Path to GC Roots.
  5. Sửa bằng Caffeine có maximumSize. Chạy lại K6 cùng kịch bản, so sánh biểu đồ heap và p95 latency trước và sau.
  6. Thử thêm: đặt -m 512m nhưng -Xmx512m để thấy container bị kill 137, rồi sửa bằng MaxRAMPercentage. Thử --cpus=1 để thấy JVM tự chọn Serial GC.
  7. Đẩy code, ảnh MAT, GC log và kết quả K6 lên GitHub kèm README. Đây là bằng chứng cụ thể khi được hỏi.

Cách ghi trong CV cho đúng với kinh nghiệm

Thay JVM Optimization bằng một trong các cách sau, tuỳ bạn đã làm tới đâu:

  • Chưa làm lab: JVM fundamentals (memory model, garbage collection)
  • Đã làm lab: JVM troubleshooting: GC log, heap dump and thread dump analysis
  • Đã xử lý sự cố thật trong dự án: giữ JVM tuning và viết hẳn một bullet trong phần dự án, có số liệu.

Ở dự án thật, bạn vẫn có những chỗ chạm tới chủ đề này để kể: job đọc log_mileage cả ngày (đọc theo trang hay load hết?), task ECS cấu hình bao nhiêu RAM và CPU (có đang vô tình chạy Serial GC?), cache từ khoá hot nằm ở Redis thay vì heap. Hỏi lại team cấu hình thật để nói cho chính xác.

Môi trường đo: OpenJDK 21.0.12 (Ubuntu build), HotSpot 64-bit, 2 vCPU, 8 GB RAM. Các chương trình thí nghiệm: LeakApp, HealthyApp, Deadlock, HotLoop, GcBench, WarmUp, Escape. Số liệu chạy một lần, dùng để minh hoạ hình dạng và mức chênh lệch, không phải benchmark chính thức.
